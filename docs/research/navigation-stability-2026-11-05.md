# Navigation stability in IGV Desktop

Research date: 2026-11-05. Live source retrieval and inspection of IGV Desktop commit `f4b78d6412fa31eaca9b5bad7b3c35a8925828da`; no application was run and no navigation behavior was measured. These findings explain mechanisms in that revision, not a guarantee for every IGV version, setting, or navigation operation.

This evidence informed Bamdalf's sampling and navigation decisions (Q70–Q79). [design.md](../design.md) is the authority for current behavior; the IGV mechanisms below are not selected implementation requirements.

## Main finding

IGV combines random downsampling with reuse of an expanded loaded interval and its packed rows. A small pan does not necessarily create a new sample or a new layout. Random selection on a new load is therefore compatible with stable nearby navigation. Reloads, packing modes, and sorting settings limit that stability. [Cache reuse and expanded loading](https://github.com/igvteam/igv/blob/f4b78d6412fa31eaca9b5bad7b3c35a8925828da/src/main/java/org/igv/alignment/AlignmentDataManager.java#L180-L271), [stored layout lookup](https://github.com/igvteam/igv/blob/f4b78d6412fa31eaca9b5bad7b3c35a8925828da/src/main/java/org/igv/alignment/AlignmentDataManager.java#L395-L401), [random seed](https://github.com/igvteam/igv/blob/f4b78d6412fa31eaca9b5bad7b3c35a8925828da/src/main/java/org/igv/alignment/AlignmentTileLoader.java#L442-L480).

## Loaded region and sample reuse

`getLoadedInterval` first looks for a cached interval containing the entire current reference-frame range. `isLoaded` uses that result, and `load` immediately returns when the range is already loaded. The track's readiness check uses the same test; IGV's repaint path schedules loads only for tracks that are not ready. Navigation within the cached range consequently avoids that alignment-query and sampling path. [Containment and early return](https://github.com/igvteam/igv/blob/f4b78d6412fa31eaca9b5bad7b3c35a8925828da/src/main/java/org/igv/alignment/AlignmentDataManager.java#L180-L234), [track readiness](https://github.com/igvteam/igv/blob/f4b78d6412fa31eaca9b5bad7b3c35a8925828da/src/main/java/org/igv/alignment/AlignmentTrack.java#L512-L529), [load scheduling](https://github.com/igvteam/igv/blob/f4b78d6412fa31eaca9b5bad7b3c35a8925828da/src/main/java/org/igv/ui/IGV.java#L1963-L1997).

The track calls `load(..., expandEnds=true)`. Away from coordinate boundaries, when the configured range cap is inactive, the query covers approximately four viewport widths in total, centered on the current viewport. That leaves about 1.5 viewport widths beyond each visible edge. This follows from the actual arithmetic, not just the source comment: for viewport width `W`, the half-width is `max(W, min(4W, configuredRange)/2)`, subject to integer-coordinate guards. The buffer is therefore not universally four viewport widths. [Track call](https://github.com/igvteam/igv/blob/f4b78d6412fa31eaca9b5bad7b3c35a8925828da/src/main/java/org/igv/alignment/AlignmentTrack.java#L524-L529), [range calculation](https://github.com/igvteam/igv/blob/f4b78d6412fa31eaca9b5bad7b3c35a8925828da/src/main/java/org/igv/alignment/AlignmentDataManager.java#L236-L263).

On a cache miss, this path loads a new expanded interval and packs it. It does not extend the old interval by fetching only its missing edge. Cache trimming retains intervals that fully contain a current frame, so this is not an unlimited history of visited regions. The renderer can temporarily obtain an overlapping old interval, but that overlap alone does not make the new viewport fully loaded. [New interval and cache trimming](https://github.com/igvteam/igv/blob/f4b78d6412fa31eaca9b5bad7b3c35a8925828da/src/main/java/org/igv/alignment/AlignmentDataManager.java#L263-L301), [overlap fallback](https://github.com/igvteam/igv/blob/f4b78d6412fa31eaca9b5bad7b3c35a8925828da/src/main/java/org/igv/alignment/AlignmentDataManager.java#L180-L195), [renderer lookup](https://github.com/igvteam/igv/blob/f4b78d6412fa31eaca9b5bad7b3c35a8925828da/src/main/java/org/igv/alignment/AlignmentTrack.java#L616-L630).

## Row reuse and its exceptions

Each loaded `AlignmentInterval` stores `PackedAlignments`. Rendering retrieves those existing groups and iterates their existing row lists; it does not invoke the packer on each paint. In modes other than `FULL`, packing operates on the loaded alignment list rather than clipping it to the current viewport. Thus, with unchanged packing/sorting options, moving inside the loaded region can translate the existing pileup without rebuilding its rows. [Stored packing](https://github.com/igvteam/igv/blob/f4b78d6412fa31eaca9b5bad7b3c35a8925828da/src/main/java/org/igv/alignment/AlignmentInterval.java#L188-L195), [layout retrieval](https://github.com/igvteam/igv/blob/f4b78d6412fa31eaca9b5bad7b3c35a8925828da/src/main/java/org/igv/alignment/AlignmentDataManager.java#L395-L401), [row rendering](https://github.com/igvteam/igv/blob/f4b78d6412fa31eaca9b5bad7b3c35a8925828da/src/main/java/org/igv/alignment/AlignmentTrack.java#L651-L670), [packing mode selection](https://github.com/igvteam/igv/blob/f4b78d6412fa31eaca9b5bad7b3c35a8925828da/src/main/java/org/igv/alignment/AlignmentPacker.java#L41-L63), [dense packing](https://github.com/igvteam/igv/blob/f4b78d6412fa31eaca9b5bad7b3c35a8925828da/src/main/java/org/igv/alignment/AlignmentPacker.java#L111-L143).

The exceptions matter:

- During horizontal dragging, the pan tool emits a panning-marked locus change. The track excludes those events from its `FULL`-mode repack and automatic-sort branch. [Pan movement](https://github.com/igvteam/igv/blob/f4b78d6412fa31eaca9b5bad7b3c35a8925828da/src/main/java/org/igv/ui/panel/PanTool.java#L111-L115), [panning event](https://github.com/igvteam/igv/blob/f4b78d6412fa31eaca9b5bad7b3c35a8925828da/src/main/java/org/igv/ui/panel/ReferenceFrame.java#L359-L362), [track event handler](https://github.com/igvteam/igv/blob/f4b78d6412fa31eaca9b5bad7b3c35a8925828da/src/main/java/org/igv/alignment/AlignmentTrack.java#L375-L388).
- On drag release, `PanTool` calls `dragStopped`, which emits an ordinary, non-panning locus change. Therefore `FULL`-mode repacking and configured automatic sorting can occur on release. The track's comment about avoiding autosort at pan completion must not be treated as stronger evidence than this call chain. `FULL` packing includes only alignments overlapping the current viewport. [Release](https://github.com/igvteam/igv/blob/f4b78d6412fa31eaca9b5bad7b3c35a8925828da/src/main/java/org/igv/ui/panel/PanTool.java#L71-L77), [completion event](https://github.com/igvteam/igv/blob/f4b78d6412fa31eaca9b5bad7b3c35a8925828da/src/main/java/org/igv/ui/panel/ReferenceFrame.java#L139-L142), [event defaults](https://github.com/igvteam/igv/blob/f4b78d6412fa31eaca9b5bad7b3c35a8925828da/src/main/java/org/igv/event/ViewChange.java#L27-L54), [FULL packing](https://github.com/igvteam/igv/blob/f4b78d6412fa31eaca9b5bad7b3c35a8925828da/src/main/java/org/igv/alignment/AlignmentPacker.java#L242-L278).
- New loads pack new rows. Changes such as grouping, pairing, or transitions to/from `FULL` also trigger packing; user sorting can change row order without resampling. These are distinct causes of visual movement. [Packing after load](https://github.com/igvteam/igv/blob/f4b78d6412fa31eaca9b5bad7b3c35a8925828da/src/main/java/org/igv/alignment/AlignmentDataManager.java#L263-L271), [pairing](https://github.com/igvteam/igv/blob/f4b78d6412fa31eaca9b5bad7b3c35a8925828da/src/main/java/org/igv/alignment/AlignmentDataManager.java#L198-L215), [display-mode changes](https://github.com/igvteam/igv/blob/f4b78d6412fa31eaca9b5bad7b3c35a8925828da/src/main/java/org/igv/alignment/AlignmentTrack.java#L463-L471), [sorting and grouping](https://github.com/igvteam/igv/blob/f4b78d6412fa31eaca9b5bad7b3c35a8925828da/src/main/java/org/igv/alignment/AlignmentTrack.java#L756-L809).

## Reloads, randomness, and zoom

A new tile constructs a new sampling map and seeds the shared random generator from the current time. Reservoir-style replacement uses random draws. A reload can therefore select different groups, including when it overlaps the previous query. The inspected loader does not carry the previous tile's keep/drop map into the new tile. This establishes no stable-sample guarantee across reload boundaries; it also does not imply every reload necessarily produces a different sample. [Tile creation](https://github.com/igvteam/igv/blob/f4b78d6412fa31eaca9b5bad7b3c35a8925828da/src/main/java/org/igv/alignment/AlignmentTileLoader.java#L124-L126), [seed and map](https://github.com/igvteam/igv/blob/f4b78d6412fa31eaca9b5bad7b3c35a8925828da/src/main/java/org/igv/alignment/AlignmentTileLoader.java#L442-L483), [sampling draws](https://github.com/igvteam/igv/blob/f4b78d6412fa31eaca9b5bad7b3c35a8925828da/src/main/java/org/igv/alignment/AlignmentTileLoader.java#L538-L575).

Zoom uses the same coordinate-containment cache test. Zooming in within the loaded interval can retain the existing sampled reads instead of automatically revealing previously omitted reads; zooming out can reuse them while the larger viewport still fits. Moving outside that range requires a new load at alignment-visible scales. Above the visibility threshold, loading and drawing alignments are suppressed. Normal zoom events can still trigger the `FULL`/sorting exceptions above. [Zoom and locus event](https://github.com/igvteam/igv/blob/f4b78d6412fa31eaca9b5bad7b3c35a8925828da/src/main/java/org/igv/ui/panel/ReferenceFrame.java#L272-L282), [centering event](https://github.com/igvteam/igv/blob/f4b78d6412fa31eaca9b5bad7b3c35a8925828da/src/main/java/org/igv/ui/panel/ReferenceFrame.java#L370-L374), [cache/visibility checks](https://github.com/igvteam/igv/blob/f4b78d6412fa31eaca9b5bad7b3c35a8925828da/src/main/java/org/igv/alignment/AlignmentDataManager.java#L220-L234), [render cutoff](https://github.com/igvteam/igv/blob/f4b78d6412fa31eaca9b5bad7b3c35a8925828da/src/main/java/org/igv/alignment/AlignmentTrack.java#L546-L551).

Explicit refresh/reload events clear the interval cache and therefore remove this reuse opportunity. [Refresh event](https://github.com/igvteam/igv/blob/f4b78d6412fa31eaca9b5bad7b3c35a8925828da/src/main/java/org/igv/alignment/AlignmentDataManager.java#L75-L84), [track reload event](https://github.com/igvteam/igv/blob/f4b78d6412fa31eaca9b5bad7b3c35a8925828da/src/main/java/org/igv/alignment/AlignmentTrack.java#L366-L373), [cache clearing](https://github.com/igvteam/igv/blob/f4b78d6412fa31eaca9b5bad7b3c35a8925828da/src/main/java/org/igv/alignment/AlignmentTrack.java#L932-L934).

## Implication for Bamdalf

The source supports separating three design choices: when a new sample is formed, whether selected groups persist during navigation, and whether surviving alignments retain their row positions. Choosing random sampling does not itself require fresh independent draws on every tiny pan, nor does a stable sample alone guarantee stable row placement. This is an inference from the separate sampling, cache, and packing paths above.

An expanded loaded region with retained sampling and packed rows is a concrete IGV precedent for nearby navigation. Copying it would still require reconciling Bamdalf's current-view budget and highest-priority selection (Q41/Q44/Q70): a sample formed over a larger loaded region is not automatically the specified sample of the current viewport.

Bamdalf's accepted continuity and fresh-layout cases are defined in [design.md](../design.md), including Q71–Q79. They do not adopt IGV's cache or packing mechanisms. Stable priorities alone do not preserve rows, and retained rows alone do not ensure that the current view has the required sample. Exact packing/state mechanisms, cache reconciliation, and resource limits need their own design and verification.
